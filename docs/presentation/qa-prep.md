# Ответы на вероятные вопросы жюри

**Чем это лучше обычного чат-бота с RAG?**
Бот только отвечает. AI-buddy доводит до результата: проверяет правила в корпоративном сервисе, готовит заявку, отслеживает статус, обновляет план. И замыкает петлю с наставником: ответ на новый вопрос становится знанием команды.

**Что если LLM ошибётся и отправит заявку?**
Не может: инструменты записи модель вызывает только с `dry_run=true`, это выставляет код оркестратора. Реальная отправка — отдельный эндпоинт, его вызывает кнопка пользователя.

**Как защищаетесь от prompt injection?**
Не полагаемся на промпт. Закрытые документы фильтруются до поиска и не попадают в контекст, инструменты фильтруются по роли на стороне сервиса, сервисы перепроверяют токен пользователя, отправка требует человека. Тест: стажёр просит методичку наставника и не получает её.

**Почему офлайн-режим, если это ИИ-помощник?**
Устойчивость и проверяемость. Модель может быть недоступна, а заявки и ответы по инструкциям должны работать. Офлайн-агент использует те же инструменты и права. С ключом работает LLM с tool calling; при сбое — автоматический резерв.

**Какую модель использовать в Авито?**
Любую с OpenAI-совместимым API и tool calling: внутреннюю, через шлюз или self-hosted (vLLM). Меняются три переменные окружения.

**Как внедрить в реальную инфраструктуру?**
MCP-адаптеры к реальным системам отсутствий и доступов с тем же контрактом (включая `dry_run`), корпоративная авторизация вместо mock-SSO, флаги из сервиса feature flags, события в clickstream. Таблица — в `docs/integration.md`.

**Почему MCP, а не прямые REST-вызовы?**
В Авито уже есть платформа ИИ-агентов с MCP. Сервисы, опубликованные как MCP, переиспользуются любыми агентами, а AI-buddy получает новые инструменты без изменения кода агента.

**Как считаете сэкономленные часы?**
Консервативно: 10 минут на рутинный вопрос без эскалации (переключение контекста + ответ), 15 минут на помощь с заявкой. Это оценка на экране; эффект меряем A/B-тестом (слайд 14).

**Что с персональными данными?**
Только синтетические данные. Больничные, зарплата и финансы вне области: ассистент направляет к HR BP. В событиях аналитики нет текста сообщений.

**Как масштабируется?**
Сервис без состояния в памяти (кроме SSE-подписок): данные в PostgreSQL, сессии в Redis. Можно ставить несколько реплик; для SSE между репликами — pub/sub в Redis (точка расширения — `events.Hub`).

**Почему покрытие считается без `cmd/`?**
Требование — покрытие прикладного кода команды. `cmd/` — только сборка зависимостей и запуск; вся логика в `internal/`, и она покрыта на 94,8%.

**Почему не Telegram-бот или мини-приложение?**
Данные о сотрудниках, заявках и доступах не должны уходить во внешний мессенджер, а учётная запись Telegram не совпадает с корпоративной — понадобилась бы отдельная авторизация в обход ролевой модели. Мы сделали ассистента независимым от канала: веб и PWA — клиенты одного API, а бот в корпоративном мессенджере подключается как ещё один клиент без изменений в агенте.

**Что бы сделали следующим?**
Подключение Confluence с правами пространств, проактивные напоминания через ИИ-крон, сценарии для наставника (черновик обратной связи, напоминания о 1:1).
