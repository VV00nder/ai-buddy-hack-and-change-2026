# Технический план AI-buddy

## Контекст
Прототип ИИ-помощника стажёра для Авито (кейс Hack&Change 2026). Пользователь — стажёр; наставник, руководитель и HR BP участвуют в отдельных сценариях. Решение должно встраиваться в существующую инфраструктуру: авторизация, данные сотрудников, ролевая модель, платформа ИИ-агентов с MCP, feature flags, clickstream, Grafana.

## Компоненты
| Компонент | Технология | Ответственность |
|---|---|---|
| `buddy` | Go 1.24, net/http | API, сессии, агент, сценарии, SSE, раздача веб-интерфейса |
| `corp` (имитация) | Go | Справочник, отсутствия, доступы, mock-SSO; опубликованы как MCP-сервер |
| Веб-интерфейс | React 19, TypeScript, TanStack Query, Zustand, Zod, esbuild | Чат, план, заявки, инструкции; экраны наставника и руководителя |
| PostgreSQL 16 | lib/pq | Сообщения, действия, план, вопросы, уведомления, FAQ, события |
| Redis 7 | go-redis | Сессии с TTL, ограничение частоты сообщений |
| LLM | OpenAI-совместимый API | Понимание запроса и выбор инструментов (опционально) |

## Ключевые решения
1. **MCP как граница с корпоративными сервисами.** Каждый сервис — MCP-сервер (`tools/list`, `tools/call`, JSON-RPC 2.0 поверх HTTP). Агент получает инструменты динамически, с фильтром по роли пользователя. Так AI-buddy подключается к платформе ИИ-агентов Авито без переделки, а новые сервисы (командировки, найм, бенефиты) добавляются регистрацией MCP-сервера.
2. **Подтверждение действий человеком.** Инструменты записи вызываются агентом только с `dry_run=true`. Результат проверки превращается в черновик `Action(status=proposed)`. Реальный вызов делает сервисный слой, когда стажёр нажимает «Отправить».
3. **Токен личности пользователя передаётся сервисам.** SSO выдаёт подписанный токен; AI-buddy передаёт его в MCP-вызовах (on-behalf-of). Сервисы сами проверяют роль и принадлежность к команде.
4. **Два режима агента.** С ключом — LLM с вызовом инструментов. Без ключа или при сбое модели — детерминированный офлайн-агент с тем же набором инструментов и прав. Жюри может проверить всё без ключа.
5. **Асинхронный ответ.** `POST /api/messages` сразу возвращает `202` с сообщением в статусе `pending`; агент работает в фоне и публикует шаги через SSE. Если SSE недоступен, интерфейс опрашивает сервер.
6. **Знания с правами.** Документы несут `audience` (роли) и `team`. Фильтрация выполняется до поиска, поэтому закрытый текст не попадает в контекст модели.
7. **Обучение на ответах наставников.** Ответ наставника можно сохранить в базу знаний команды; следующий похожий вопрос закрывается без наставника.

8. **Агент не привязан к каналу.** Вся логика за HTTP API; веб и PWA — клиенты. Новый канал (бот корпоративного мессенджера) — адаптер к тем же эндпоинтам и потоку событий. Публичные мессенджеры не используются: данные не покидают контур компании.

## Модель данных (PostgreSQL)
`step_states(user_id, step_id, status, note, updated_by, updated_at)`, `messages`, `actions`, `questions`, `notifications`, `faq`, `events`. Поля для выборок вынесены в колонки, вложенные структуры хранятся в `jsonb`. Миграция `backend/internal/store/migrations/001_init.sql` применяется при старте.

## Нефункциональные требования
- Локальные операции < 1 с: проверено e2e; типичный ответ офлайн-агента — десятки миллисекунд.
- Таймауты: MCP 10 с, LLM 40 с, обработка сообщения 60 с; по таймауту сообщение получает статус `error` с понятным текстом.
- Rate limit: 20 сообщений в минуту на пользователя (Redis).
- Безопасность: cookie `HttpOnly` + `SameSite=Lax`, обязательный заголовок `X-Requested-With` для изменяющих запросов (CSRF), CSP, лимиты размера тела и полей.
